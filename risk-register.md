# Risk Register

## Overview

This risk register synthesises findings from the Discovery (phase-1), Exploration (phase-2), Clarification (phase-3), Architecture (phase-4), and Cluster Inventory audit artifacts for the Bugzilla-to-Evergreen migration. The inputs cover 7 bounded contexts across a ~111 kLOC Perl monolith being re-architected as CQRS/Event Sourcing microservices.

The highest concentration of risk sits in **service-bug**: the Bugzilla::Bug god-object (5 123 LOC) holds most of the system's behavioural complexity, cross-table side effects, and undocumented invariants. Wire-format compatibility between service-bug and its 4 consumers is the broadest event-contract surface in the architecture. On the operational side, the data migration from 60+ relational tables into event streams is a single, non-resumable cutover with no rollback path.

## Tribal Knowledge Dependencies

- **R-009 — All clusters rated `unknown` stability** (cluster-inventory.md §"Stability Ratings"): The entire codebase was imported as a single bulk snapshot with zero git history. There are no author attribution signals, no churn metrics, and no test proximity data for 6 of 7 services. The original authors of the Perl modules are unknown — the cluster inventory reports `(unversioned)` for every file. This means the migration team has no way to identify which developers hold institutional knowledge about each subsystem. Mitigate by treating the source code itself as the sole knowledge artifact and investing heavily in exploration documentation before implementation.

- **R-001 — Bug.pm cross-table side effects** (exploration.md §"Cross-table side effects", cluster-inventory.md "Bugzilla::Bug — god-object coupling"): Bug.pm (5 123 LOC) fires email notifications, fulltext index updates, extension hooks, and activity logging synchronously inside its mutation methods. No single person likely holds a complete mental model of all these interactions. The exploration phase documented them, but the risk remains that a subtle side effect (e.g., `see_also` recursive reverse-linking described in R-008) is missed during decomposition.

- **R-002 — Three-way group permission split** (exploration.md §SC2 "Critical decomposition note", clarification.md Q5): The original `Bugzilla::User` god-object held group membership, product-level group configuration, and bug-level group enforcement in a single module. The migration splits this across three services. The tribal knowledge of "which service owns which part of the permission check" is new — there is no existing developer who understands the split because it hasn't been implemented yet. Mitigate with clear ADR documentation and cross-service integration tests.

- **R-007 — Password hash auto-upgrade side effect** (exploration.md §"Password hash auto-upgrade on login", user-accounts-auth.md line 374): The legacy `Verify::DB` module transparently rehashes passwords on successful login. This is a write side effect hidden inside what appears to be a read-only authentication check. Without the exploration slice documenting this, the migration team would likely miss it, resulting in users with legacy hashes being unable to authenticate after migration. The recommended mitigation (Q14) is a backward-compatible verifier with transparent rehash.

## Hidden Behaviors

- **R-008 — `see_also` recursive reverse-linking** (cluster-inventory.md "`Bugzilla::Bug` — `see_also` recursive behavior", exploration.md §"Cross-table side effects"): When adding a local bug URL as a "see also" reference, Bugzilla automatically adds the reverse link on the target bug — a cross-aggregate mutation within the monolith. This is not obvious from the `bug_see_also` table schema (which stores unidirectional rows). The Evergreen migration must implement this as an event-driven subscription handler to avoid losing the bidirectional behaviour.

- **R-007 — Password hash auto-upgrade on login** (exploration.md §"Password hash auto-upgrade on login", user-accounts-auth.md line 374): The authentication verify step in `Verify::DB` writes an upgraded password hash to the database on successful login when a legacy algorithm is detected. This is a write side effect hidden inside a read path. In Evergreen's event-sourced model, this must become an explicit `PasswordRehashed` event emitted by the `AuthenticateUser` command handler.

- **R-013 — Comment privacy toggle triggers fulltext re-index** (cluster-inventory.md "Comment privacy toggle triggers fulltext re-index"): Changing `isprivate` on a comment calls `$self->bug->_sync_fulltext(update_comments => 1)`, synchronously re-indexing the parent bug's entire fulltext search blob. This cross-entity side effect means privacy changes have a search-impact cost that is invisible from the comment module's public interface. The Evergreen migration must route this through an event chain to the search service.

- **R-006 — Mandatory group cascading retroactively mutates bugs** (cluster-inventory.md "Mandatory group cascading", product-hierarchy.md line 289): When a group's `membercontrol` is changed to MANDATORY for a product, all existing bugs in that product are retroactively added to the group — a cross-aggregate side effect triggered from the product domain. This is a batch mutation with no rollback: if it fails partway through, some bugs have the group restriction and others don't.

- **R-014 — Memcached status workflow caching with manual invalidation** (cluster-inventory.md "Memcached as global shared state"): Status workflow states are cached in memcached with keys like `status_bug_state_open`; invalidation occurs on status create/delete events. In Evergreen, there is no shared cache — each service projects its own read models. The hidden behavior is that any status workflow change in the monolith immediately affects all concurrent requests via memcached invalidation. In Evergreen's eventually consistent model, there is a propagation delay that the original system did not have.

- **R-016 — Extension hook shared mutable state** (cluster-inventory.md "Extension hook system — shared mutable state"): `Bugzilla::Hook::process()` passes a shared mutable `$args` hashref to all extensions in load order. Extensions can modify the hashref, and downstream extensions see those modifications — cooperative mutation with no ordering guarantees. This is a subtle concurrency contract that has no direct equivalent in Evergreen's event-driven architecture. The ADR-003 decision to map extensions to event subscriptions deliberately drops this semantics.

## Wire-Format Compatibility

- **R-004 — Event naming inconsistencies across service docs (Resolved 2026-05-06)** (interaction-map.md §"Naming Inconsistencies"): Four naming mismatches between service architecture documents have been reconciled by aligning on canonical names. Canonical choices: `BugProductChanged` (retired alias `BugMoved`, 85 vs 82 corpus refs and more semantically precise); `CommentTagAdded` (retired alias `CommentTagged`, 53 vs 20 refs and matching the canonical owner service-comment); `EmailPreferencesUpdated` (retired alias `UserPreferencesChanged`, 48 vs 28 refs and matching the canonical owner service-user); and the specific `AttachmentFlagRequested` / `BugFlagRequested` / `AttachmentFlagGranted` / `AttachmentFlagDenied` / `BugFlagGranted` / `BugFlagDenied` events (retired generic aliases `FlagSet` / `FlagRequested`, which never existed as actual emitted events). All `@EventHandlerDecorator` strings in the audit and architecture corpus now match the canonical event names emitted by the owning aggregates. The recommended cross-service contract-lint check still stands as preventive scaffolding for future regressions.

- **R-005 — `bug.Events.BugCreated` payload drift across 4 consumers** (interaction-map.md §"Events by Producer — service-bug"): `BugCreated` is consumed by service-notification, service-search, service-comment, and service-attachment. Adding or removing a payload field without versioning breaks at least one consumer's projection silently. The recommended mitigation (ADR-012: carry full diff payloads) increases event size but eliminates query-back coupling. An event envelope version field is needed before any payload change.

- **R-019 — Bug-level flag events cross the service-bug / service-attachment boundary** (interaction-map.md §"service-bug Subscriptions", clarification.md Q4): `attachment.Events.BugFlagRequested`/`BugFlagGranted`/`BugFlagDenied`/`BugFlagCleared` are published by service-attachment but consumed by service-bug for a projected `BugFlagListReadModel`. This means bug-level flag state has a dual representation: the authoritative state in service-attachment's Flag aggregate, and a projected copy in service-bug's read model. If the event payload changes in service-attachment without updating service-bug's projection handler, bug-level flags displayed on bug detail pages will diverge from actual flag state.

- **R-015 — Synchronous cross-service query for bug existence** (interaction-map.md "Synchronous Cross-Service Queries" table): `service-comment` and `service-attachment` both make synchronous queries to `service-bug` during command handling to validate bug existence. These are the only synchronous cross-service calls permitted during command handling (per ADR-012). If service-bug's API contract changes (e.g., `GetBug` response schema), both services break at runtime. Mitigate by projecting local `BugSummaryReadModel` in each consumer and eliminating the synchronous call.

- **R-006 — `product.Events.GroupControlsUpdated` triggers mandatory-group cascade** (interaction-map.md §9 "Product Creation Saga", exploration.md §"Mandatory group cascading"): The `GroupControlsUpdated` event carries the product ID, group ID, and new control settings. When `membercontrol` changes to MANDATORY, service-bug must retroactively add all existing bugs to the group. The event payload must include enough context (product ID, group ID, old and new control values) for service-bug to execute the cascade correctly. If the payload is underspecified, the cascade may miss bugs or apply the wrong group restriction.

## Operational Risks

- **R-010 — One-time freeze-extract-transform-load cutover with no rollback** (data-migration-strategy.md §"Migration Approach — FETL"): The migration strategy is a single cutover: freeze Bugzilla, extract data, transform to events, load into Evergreen, switch DNS. If the migration fails after partial event loading, there is no rollback mechanism — the event store cannot be selectively reversed without replaying all aggregates. Mitigate with full dry-run on a staging copy, event-count validation, and maintaining the frozen Bugzilla instance as a read-only fallback for 30 days.

- **R-018 — Binary attachment migration is non-transactional** (data-migration-strategy.md §"Binary Attachment Migration"): Attachments are migrated from DB BLOBs and local filesystem to S3/MinIO. This is an out-of-band sync with no transactional guarantee — a partial upload leaves some attachments unretrievable in the new system. With potentially 100K+ attachments, the probability of at least one upload failure is non-trivial. Mitigate with a migration manifest tracking per-file SHA-256 checksums, retry logic, and a post-migration verification step that compares counts and checksums.

- **R-012 — Orphan version/milestone references block data migration** (data-migration-strategy.md §"Step 3: Handle Orphan References"): Bugs may reference version or milestone strings that no longer exist in the `versions`/`milestones` tables (e.g., a version was deleted but bugs still reference it). The string-to-ID lookup will fail for these rows. This is HIGH likelihood because the Bugzilla schema allows this orphan state — there is no FK constraint enforcing version string integrity. The mitigation (placeholder records) requires pre-scan detection before migration day.

- **R-011 — Large event streams from historical activity replay degrade rehydration** (data-migration-strategy.md §"Historical Data Handling"): The `bugs_activity` table can have millions of rows for large Bugzilla instances. Replaying every historical field change as an individual event creates extremely long aggregate streams. While the snapshot + activity hybrid approach mitigates rehydration cost, the total event store size may be orders of magnitude larger than the source database, affecting storage costs and backup/recovery times.

- **R-020 — Secrets management gap for `localconfig` replacement** (cluster-inventory.md "`localconfig` read once at startup"): Bugzilla reads DB credentials, SMTP settings, and other secrets from a static `localconfig` file at process startup. Evergreen services need equivalent configuration, but the platform's secret rotation mechanism is unspecified. If secrets require a service restart to take effect, operational secret rotation (e.g., after a credential leak) requires coordinated downtime across all services.

## Methodology Notes

Likelihood was rated H when the cluster inventory reported `unknown` stability (all 7 clusters), when clarification.md flagged the item as a HIGH-priority open question, or when the failure mode is already observable in the source artifacts (naming inconsistencies, orphan references). Impact was rated H when the risk involves silent data loss (search results exposing private comments), security boundary violations (group visibility), or blocks an entire migration path (FETL cutover failure). When sources disagreed (e.g., exploration.md flagged a concern but clarification.md resolved it with a recommendation), the risk was retained but the recommendation was folded into the mitigation column.

One risk was considered but excluded: the Voting extension migration (clarification.md Q13). All five bundled extensions are disabled, and the recommendation is to defer entirely. Including it would be speculative — there is no evidence of active use in the source artifacts.
